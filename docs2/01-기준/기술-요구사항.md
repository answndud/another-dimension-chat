# 기술 요구사항

작성 기준: 2026-08-23 개편 완료 후 현재 코드 상태

## 1. 현재 구현 스택

| 영역 | 기술 | 책임 |
|---|---|---|
| daemon (`apps/daemon`) | Rust workspace, Tokio/Axum, OpenMLS 0.8, libcrux, rustls | 신원·세션·암호화·저장·로컬 API·WebSocket push |
| relay (`apps/relay`) | Rust, Axum, bounded in-memory/persisted state | 초대 rendezvous(다중 response)·opaque envelope·blob 전달 |
| web (`apps/web`) | React 19 + TypeScript 5.8 + Vite 6 | 화면·입력·상태 표시·WebSocket 실시간 수신 |
| tools (`apps/tools`) | Rust CLI | static asset, release manifest, archive 보조 |
| 저장 | daemon 소유 AES-256-GCM 암호화 store | identity, contacts, transcripts, attachments |

Node.js 서버 런타임, Tauri, browser Olm은 현재 release 실행 경로가 아니다.
OpenMLS를 애플리케이션 신뢰성의 증거로 오해하지 않으며, 이 프로젝트의 identity
binding, 저장 transaction, bridge, delivery composition은 별도로 검토해야 한다.

### 웹 프론트엔드 구조 (P1 완료)

```text
apps/web/src/
  main.tsx                 — React root, useDaemon hook으로 화면 분기
  screens/
    Setup.tsx              — 최초 프로필 설정 화면
    Ready.tsx              — 대화·기기·보안·상태 4-view 워크스페이스 + 실시간 배너
  components/
    ContactList.tsx        — 연락처 목록·선택
    Conversation.tsx       — 메시지 표시·입력·전송
    GroupInvite.tsx        — 그룹 멤버 다중 선택 초대 UI
  hooks/
    useDaemon.ts           — daemon bridge 초기화·상태 관리 중앙 hook
    useWebSocket.ts        — /local-api/events 구독, 재연결, 메시지 동기화
    usePolling.ts          — (레거시, WebSocket으로 대체됨)
  lib/
    daemon-bridge.ts       — 타입 안전한 daemon REST API 클라이언트
    errors.ts              — 오류 코드 → 사용자 메시지 매핑
```

vanilla JS 파일(`main.js`, `daemon-controller.js`, `daemon-view.js` 등)은 React
전환이 완료되었으며 새 코드에서 import하지 않는다. 완전 제거는 별도 정리 slice다.

## 2. 로컬 bridge 요구사항

- daemon은 기본적으로 `127.0.0.1`/`::1`에만 listen한다.
- 시작 시 생성된 bootstrap secret은 URL fragment로만 전달한다.
- bootstrap은 exchange 직후 폐기하고 짧은 수명의 HttpOnly, SameSite 세션으로 교체한다.
- 모든 변경 요청은 CSRF token을 요구하고 `Origin`·`Host`를 정확히 검사한다.
- 허용 UI 버전과 CSP를 확인하며 임의의 외부 script·CDN·frame을 허용하지 않는다.
- **WebSocket `/local-api/events`도 동일한 session cookie + Origin + Host + UI version
  검증을 통과해야 upgrade된다** (P4 완료, focused test로 고정).
- daemon 재시작·lock·session revoke 시 기존 세션은 사용할 수 없어야 한다.
- 브라우저는 private key, database key, MLS state를 장기 보관하지 않는다.

## 3. 실시간 레이어 요구사항 (P2 완료)

- daemon maintenance tick(15초 주기)에서 relay sync로 새 메시지를 처리하면
  broadcast channel을 통해 모든 WebSocket subscriber에 `messages_updated` payload를
  전송한다.
- 클라이언트 `useWebSocket.ts` hook이 payload를 받으면 활성 대화만 필터링해
  `syncDelivery` → 메시지 병합(`mergeDaemonMessages`로 중복 방지) → 즉시 render한다.
- heartbeat: 20초마다 WebSocket ping frame 전송.
- 재연결: close 이벤트 후 3초 대기 후 재시도. 재연결 성공 시 missed event 복구를 위해
  활성 대화 전체 sync 1회 실행.
- relay pairing response는 invite당 다중 response 배열을 지원해 그룹 초대 시 여러
  멤버의 key-package와 welcome이 공존할 수 있다 (P5 완료).

## 4. 릴레이 경계와 제한

현재 코드의 대표 제한은 다음과 같다. 변경 시 `apps/relay/src/main.rs`의 상수와 이
문서를 함께 갱신한다.

| 항목 | 제한 |
|---|---:|
| opaque envelope | 96 KiB |
| 일반 request body | 192 KiB |
| inbox 보관 항목 | 256개 |
| invite 보관 항목 | 256개 |
| 요청 빈도 | 120회/window |
| 첨부 blob | 32 MiB 이하 |

relay는 account directory·plaintext archive·private-key store·push service가 아니다.
capability URL은 bearer secret이므로 로그와 모니터링 URL에 넣지 않는다. 읽기/ack
capability와 제출 capability를 혼동하지 않으며, 재전송은 동일 바이트일 때만 멱등
처리한다.

relay의 invite rendezvous는 invite당 하나의 `pairingResponse`가 아니라
`pairingResponses` 배열을 유지해, 그룹 소유자가 여러 멤버의 key-package와 welcome을
순서대로 게시할 수 있다 (P5 완료).

## 5. MLS 그룹 요구사항 (P3/P5 완료)

- `add-member` 라우트는 단일 `key_package` 문자열 또는 `key_packages` 배열을 모두
  수용한다. 배열 입력 시 batch welcome 생성.
- `pending_key_packages: Vec<Vec<u8>>`로 승인 대기 멤버를 누적 관리하고, 승인 시
  전체를 한 번에 add-member 처리해 welcomes를 각 멤버의 rendezvous에 전송한다.
- `pending_rendezvous_codes: Vec<String>`로 동시 초대 코드를 추적하며, complete-session
  시 사용된 코드만 제거한다.
- Established 페어링에서 추가 멤버 stage/approve를 허용하되, 동일 account 재바인딩은
  `BindingChanged`로 거부한다 (첫 peer의 binding 우선).

## 6. 저장·키 요구사항

- 프로필 암호문구는 daemon이 암호학적으로 랜덤하게 생성한다.
- passphrase 기반 키 파생에는 Argon2id를 사용한다.
- 저장 데이터는 AES-256-GCM과 무결성 검사를 사용한다.
- macOS에서는 선택적으로 Keychain 경계를 사용할 수 있다.
- lock/stop 시 메모리의 사용 가능한 키를 지우고 새 인증을 요구한다.
- recovery export는 암호화된 snapshot이며 live relay queue나 삭제 데이터를 복구한다는
  의미가 아니다.
- 복구·wipe는 사용자가 파일을 별도 오프라인 매체에 보관하는 운영 절차와 함께 사용해야
  한다.

## 7. 오류 처리

입력 형식 오류, 만료, capability 실패, stale session, 신원 변경, 암호 검증 실패,
스토리지 손상은 서로 다른 오류로 반환한다. 모호한 실패를 성공으로 처리하지 않으며,
프로토콜 상태를 저장하기 전에 검증하고 checkpoint transaction이 실패하면 상태 전이를
커밋하지 않는다.

## 8. 배포·용량 요구사항

- release에는 daemon, relay, tools와 정적 web asset(Vite 빌드 산출물 포함)만 넣는다.
- Node runtime과 `target/`, `.build-cache/`, logs, local profile은 archive에서 제외한다.
- build는 `CARGO_BUILD_JOBS=2`, `CARGO_INCREMENTAL=0`을 기본으로 사용한다.
- 대상별 캐시는 `CARGO_TARGET_DIR`로 한 곳에 제한하고, release 후 재생성 가능 산출물을
  정리한다.
- `scripts/build_client_release.sh`와 `scripts/build_release.sh`는 archive 크기와
  secret 파일 포함 여부를 실패 조건으로 검사한다.

## 9. 변경 시 필수 확인

프로토콜·키·bridge·relay 제한·release 경계 중 하나를 바꾸면 소스, 관련 문서,
`reference/PRODUCT_BOUNDARY.md`, 최소 smoke를 한 변경 단위로 갱신한다. 새 crate나
런타임을 추가할 때는 CPU·디스크·공급망 비용과 대체 가능성을 먼저 기록한다.
