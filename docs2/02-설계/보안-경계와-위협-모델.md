# 보안 경계와 위협 모델

작성 기준: 2026-08-23 개편 완료 후 현재 코드 상태

## 1. 보호 자산

- account root와 device private key
- OpenMLS group state와 메시지 평문
- 프로필 암호문구·database key·recovery material
- 연락처와 safety number 상태
- 암호화 첨부파일과 파일 키
- relay capability, local bootstrap URL, release signing trust

## 2. 방어 대상으로 보는 공격자

| 공격자 | 방어 목표 |
|---|---|
| relay 운영자 | 평문·개인키·연락처 목록을 받지 않음 |
| 네트워크 감청자 | TLS와 envelope 무결성으로 변조·내용 노출 제한 |
| 초대 탈취자 | 만료·1회 사용·서명·safety number로 승인 전 차단 |
| 악성 relay 응답 | daemon이 서명·binding·상태를 독립 검증 |
| 로컬 다른 웹사이트 | Origin/Host/CSRF/일회성 bootstrap으로 bridge 호출 제한 |
| WebSocket 무단 구독자 | session cookie + Origin + Host + UI version 4중 검증 |
| 잘못된 release 파일 | manifest·hash·서명·외부 fingerprint 절차로 설치 전 확인 |

## 3. 보호하지 못하는 상황

악성코드가 실행 중인 Mac을 장악하거나 키 입력·화면을 훔치면 daemon이 복호화한 순간의
평문을 보호할 수 없다. 상대방이 복사·촬영하는 행위, 글로벌 트래픽 분석, 서비스 거부,
검열, 운영 호스트 자체의 IP·접속 시각 관찰도 해결하지 않는다. 브라우저 bundle이 변조된
경우 키를 직접 읽지 못하더라도 unlocked session의 입력과 출력을 조작할 수 있으므로
release UI trust가 중요하다.

## 4. 주요 통제

### 신원·초대

Account/device 공개키와 초대가 서명으로 묶이고, relay origin과 만료·재사용 여부를
검사한다. 코드를 아는 것만으로 안전한 상대라는 뜻이 아니므로 safety number를 별도
채널에서 대조한 뒤 승인한다.

그룹 확장 후에도 이 원칙은 유지된다. 그룹 소유자는 Established 페어링에서 추가 멤버의
key package를 승인할 수 있지만, 동일 account에 대한 재바인딩은 `BindingChanged`로
거부되며 첫 peer의 relay origin·inbox binding이 우선한다.

### 로컬 bridge

bootstrap fragment는 서버 로그에 일반 요청으로 전송되지 않지만 브라우저 기록과 화면에는
남을 수 있는 bearer secret이다. exchange 후 URL에서 제거하고 session cookie로 교체한다.
CORS를 넓게 열지 않고 WebSocket·API에도 동일한 origin 정책을 적용한다.

WebSocket `/local-api/events` upgrade는 HTTP API와 완전히 동일한 `authorize` 절차를
통과한다. session cookie 누락, Origin 불일치, Host 불일치, UI version 불일치 중 하나라도
실패하면 upgrade 전에 401로 거부된다 (focused test로 고정).

### 저장·잠금

암호화 store와 Argon2id 기반 키 파생을 사용한다. lock은 새 API 요청을 거부하고 메모리 키를
지우는 운영 상태다. OS 수준의 swap, crash dump, 강제 종료 후 완전한 secure deletion을
보장한다고 주장하지 않는다.

### Relay

capability를 아는 요청만 제한된 queue/blob을 조작할 수 있다. body·envelope·blob·queue·
invite·rate를 bounded로 유지해 무제한 디스크·메모리 고갈을 피한다. 같은 identifier에 다른
bytes를 재제출하는 충돌은 거부한다.

그룹 rendezvous의 다중 response 배열은 invite 소유자만 게시 권한을 가지며, 각 response는
kind 필드(`key-package`, `welcome`)로 구분된다. relay는 내용을 해석하지 않고 크기·개수만
제한한다.

## 5. 고위험 승인에 필요한 별도 증거

현재 구현 게이트 통과와 별개로 독립 암호·코드 review, 외부 Chromium/macOS 실행 evidence,
release signing key의 두 채널 신뢰, incident exercise, 업데이트·복구 운영 검토가 필요하다.
이 항목들은 저장소 내부 문서나 자체 smoke만으로 완료할 수 없으며, 완료 전 high-risk mode를
켜지 않는다.

## 6. 검토 규칙

새 기능이 어느 자산을 읽고 쓰는지, 어느 경계를 넘는지, 실패 시 어떤 상태가 남는지를 먼저
기록한다. "암호화했다"는 설명만으로 위협이 사라졌다고 판정하지 않으며, 메타데이터·endpoint·
release trust를 별도 항목으로 검토한다.
