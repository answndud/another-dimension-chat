# 아키텍처 개요

작성 기준: 2026-08-23 개편 완료 후 현재 코드 상태

## 1. 전체 구성

```text
Chromium
  │ one-time bootstrap → authenticated loopback session
  │ WebSocket /local-api/events (실시간 push)
  ▼
Rust daemon (사용자 Mac)
  ├─ account/device identity
  ├─ pairing/contact/safety number
  ├─ OpenMLS session과 메시지 암복호화
  ├─ encrypted local store
  ├─ attachment chunk encryption
  ├─ delivery/recovery/lock authority
  └─ broadcast events → WebSocket subscribers
        │ HTTPS + explicit TLS pin
        ▼
Rust relay (사용자 운영 또는 신뢰 확인)
  ├─ invite rendezvous (다중 pairing responses)
  ├─ opaque envelope queue
  └─ encrypted attachment blob
```

핵심 원칙은 UI가 보안 상태의 소유자가 아니라는 점이다. 브라우저는 daemon이 허용한
화면을 표시하고 입력을 전달한다. relay는 전달 경로일 뿐이며 계정 신원과 메시지 평문을
중앙에서 관리하지 않는다.

## 2. 책임 분리

### Web (`apps/web` — React + TypeScript)

렌더링, 입력 검증의 1차 피드백, session cookie 보유, 메시지·첨부 상태 표시,
WebSocket 이벤트 구독을 담당한다. 장기 키 생성·복호화·MLS transition·복구 키 처리는
담당하지 않는다.

- `useDaemon.ts`: daemon bridge 초기화·전역 상태 관리. React 컴포넌트 라이프사이클에
  바인딩되며, 화면 분기(setup/ready/error 등)를 결정한다.
- `useWebSocket.ts`: `/local-api/events` 구독. `messages_updated` 수신 시 활성 대화만
  필터링해 syncDelivery → mergeDaemonMessages로 중복 없이 UI 갱신. 재연결 시 missed
  event 복구.
- `daemon-bridge.ts`: 타입 안전한 REST 클라이언트. CSRF token 자동 갱신, 오류 코드
  매핑 포함.

### Daemon (`apps/daemon`)

모든 보안 결정의 권위자다. profile/device identity, signed pairing, safety number,
OpenMLS group, local encrypted store, attachment encryption, relay binding, lock,
recovery, delivery state를 소유한다.

주요 모듈:

| 모듈 | 책임 |
|---|---|
| `bridge.rs`, `bridge_http.rs`, `http_server.rs` | loopbridge 인증·CSRF·routing |
| `http_server.rs::websocket_events` | `/local-api/events` upgrade + broadcast push |
| `authority.rs` | invite 생성·검증, 페어링 상태 머신, 연락처, 그룹 멤버 승인 |
| `pairing.rs` | peer 검증·safety number·승인 상태 전이 |
| `mls_session.rs`, `mls_routes.rs` | OpenMLS group create/join/send/receive/add-member |
| `delivery.rs`, `delivery_routes.rs` | 전달 ledger·envelope 제출·sync |
| `storage.rs` | AES-256-GCM 암호화 store와 transaction |
| `maintenance.rs` | 주기적 relay sync + WebSocket broadcast 트리거 |
| `relay_http.rs` | relay REST 클라이언트 (TLS pin 적용) |

### Relay (`apps/relay`)

초대 코드와 opaque 전달물을 TTL·크기·개수·빈도로 제한한다. invite rendezvous는 invite
당 `pairingResponses: Vec<Value>` 배열을 유지해 그룹 소유자가 여러 멤버의 key-package와
welcome을 순서대로 게시할 수 있다. relay가 정상적으로 동작해도 daemon의 암호 검증과
수신 승인이 없으면 메시지 평문을 만들 수 없어야 한다. 운영자는 그래도 IP·시각·크기
메타데이터를 관찰할 수 있다.

### Tools와 scripts

정적 web asset(Vite 빌드 산출물 포함)을 복사하고 release archive/manifest를 만들며,
실행 중인 보안 권한을 갖지 않는다. launcher는 사용자가 daemon과 relay를 일관되게
시작·중지하고 상태를 확인하도록 돕는 얇은 운영 계층이다.

## 3. 실시간 메시지 흐름 (P2 완료)

```text
[수신 경로]
relay inbox → maintenance tick(15s) → process_inbox_items()
  → 새 메시지 처리 성공 시 broadcast channel send("messages_updated")
    → websocket_events()의 handle_socket()이 수신
      → 클라이언트 useWebSocket.ts가 message 이벤트 수신
        → 활성 대화 필터링 → bridge.syncDelivery() → 병합 → render()

[발신 경로]
브라우저 입력 → bridge.sendMessage(conversationId, text)
  → daemon MLS encrypt → local transcript 기록
    → bridge.postDelivery(peerInboxUrl, ciphertext) → relay inbox
```

relay ACK는 "relay가 보관 또는 제출을 처리했다"는 뜻이지 "상대 사람이 읽었다"는 뜻이
아니다. 상대 daemon의 수신·복호화·로컬 저장 상태와 분리해 표시한다.

## 4. 첨부 흐름

파일은 daemon에서 랜덤 파일 키로 청크 암호화한다(64 KiB chunk). relay에는 암호화 blob만
올리고, blob 식별자·파일 키·원본 이름 등 필요한 descriptor는 메시지 암호문 안에 넣는다.
수신 daemon은 blob을 받아 chunk 순서·길이·AEAD tag를 검증한 뒤에만 임시 파일을 복원한다.
파일명과 MIME을 relay metadata로 신뢰하지 않는다. 최대 첨부 크기는 32 MiB다.

## 5. 상태 소유권

| 상태 | 소유자 | 브라우저가 직접 수정 |
|---|---|---|
| 계정·기기 키 | daemon store | 불가 |
| MLS epoch/ratchet | daemon store | 불가 |
| 연락처 승인 | daemon store | daemon command를 통해서만 |
| UI session | daemon bridge | cookie 사용만 |
| WebSocket 구독 | daemon http_server | subscribe/unsubscribe만 |
| relay queue | relay | opaque payload만 |
| 표시 필터·입력 draft | web | 가능하지만 보안 상태 아님 |

## 6. 실패 격리

잘못된 relay 응답, 변조된 envelope, stale epoch, 손상된 store, session 만료는 부분
성공으로 삼지 않는다. 해당 항목을 폐기하거나 전송을 중단하고, 사용자가 재검증·재시작·
복구 중 하나를 선택할 수 있는 상태로 남긴다.

WebSocket 끊김은 치명적 실패가 아니라 성능 저하다. 재연결 후 다음 maintenance tick에서
sync가 복구하므로 데이터 손실은 발생하지 않으며, UI 배너로 사용자에게 현재 상태를
알린다.
