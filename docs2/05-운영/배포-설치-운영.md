# 배포·설치·운영

작성 기준: 2026-08-23 개편 완료 후 현재 코드 상태

## 1. 지원 범위

현재 문서화된 실행 환경은 Apple Silicon macOS와 Chromium 계열 브라우저다. 배포 모드는
`private-trusted` 제한 배포까지만 고려하며, `public`·`high-risk-disabled` 전환은 독립
검토·운영 trust·외부 실행 증거가 생기기 전까지 금지한다.

## 2. 배포 구성

```text
private release archive
  ├─ another-dimension-daemon (Rust binary)
  ├─ another-dimension-relay (Rust binary)
  ├─ another-dimension-tools (Rust binary)
  ├─ static web assets (Vite 빌드: apps/web/dist/)
  └─ launcher scripts
       ├─ user Mac: daemon + Chromium
       └─ relay host: Rust relay
```

release archive에는 Node.js runtime, `node_modules`, Cargo toolchain이 포함되지 않는다.
압축 해제 크기는 약 7 MiB이며 50 MiB 상한을 빌드에서 강제한다.

## 3. 빌드 절차

```sh
# 1. 웹 UI 빌드 (React + Vite)
cd apps/web && npm install && npm run build && cd ../..

# 2. Rust 바이너리 빌드
CARGO_BUILD_JOBS=2 CARGO_INCREMENTAL=0 \
  cargo build --workspace --release --locked --offline

# 3. release archive 생성·검증
scripts/build_release.sh --release
```

## 4. relay 운영

```sh
AD_RELAY_BIND_HOST=0.0.0.0 AD_RELAY_PORT=19540 \
  AD_RELAY_DATA_DIR=/secure/relay-data \
  ./bin/another-dimension-relay
```

- data directory의 `inbox-capability` 파일은 bearer secret이다. 로그·모니터링에 노출하지
  않는다.
- relay 재시작 시 기존 state 파일(`relay-inbox.json`, `invite-codes.json`)을 보존하면
  envelope·invite가 유지된다.
- health check: `GET /api/v1/health`, info: `GET /api/v1/info`

## 5. daemon 운영

```sh
printf '%s' "$(cat /secure/profile.passphrase)" | ./bin/another-dimension-daemon serve \
  --data-dir "$HOME/.local/share/another-dimension/alice" \
  --port 1420 \
  --ui-dir /path/to/apps/web/dist \
  --relay-origin https://relay.example.com \
  --inbox-url https://relay.example.com/api/v1/inbox/CAPABILITY \
  --relay-public-key HEX_KEY \
  --relay-public-key-fingerprint HEX_FINGERPRINT
```

daemon 시작 후 터미널에 `open once:` URL이 출력되면 이를 사용자에게 별도 채널로 전달해
브라우저에서 한 번 열게 한다. bootstrap exchange 후 같은 URL은 재사용할 수 없다.

## 6. 업그레이드 절차

1. 기존 data directory를 백업한다.
2. 새 release archive를 받아 manifest를 검증한다.
3. release notes의 storage/protocol 호환성 및 복구 주의를 읽는다.
4. relay를 먼저 새 binary로 시작하고 health/info를 확인한다.
5. daemon을 새 binary로 시작하고 기존 profile을 읽을 수 있는지 확인한다.
6. safety number·device 상태·메시지 transcript가 예상되는지 확인한다.
7. 이상이 있으면 새 profile을 계속 사용하지 말고 incident 절차로 전환한다.

## 7. 운영 로그와 개인정보

로그에는 timestamp·일반 오류 분류·revision만 남긴다. 메시지 본문, passphrase, private key,
local URL, invite code, inbox/read capability, 파일명과 원본 metadata를 남기지 않는다.
디버그 로그를 켠 채로 실제 대화를 운영하지 않는다.

## 8. 운영 중단 기준

release fingerprint 불일치, 예상하지 못한 UI, relay capability 유출, safety number 불일치,
store corruption, 반복적인 authenticated decryption 실패가 있으면 즉시 메시지 전송을
멈춘다. 원인을 확인하기 전 기존 data directory를 덮어쓰지 않는다.
